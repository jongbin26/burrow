# React

React에서 상태를 어디에 두고, 언제 그리고, 무엇을 피하나.
원칙 자체는 링크한 dev-core 스킬이 가진다. 여기는 React에서의 구현과 함정만 둔다.

## 1. 상태와 로직은 수명과 사용 범위가 맞는 곳에 둔다

원칙: module-boundaries 1, 4
화면 하나에서만 쓰이고 그 화면과 함께 생기고 사라지는 상태는 컴포넌트와 훅에 두는 게 맞다. 언마운트될 때 함께 정리하는 것도 맞다.
반대로 화면보다 오래 살아야 하거나, React 밖에서도 쓰이거나(다른 렌더러, 비 UI 소비자, React 없는 테스트), 규칙이 커서 reducer가 도메인 규칙을 떠안기 시작하면, React를 모르는 모듈로 옮기고 React는 구독해서 그리기만 한다.
판정 질문: 이 상태가 컴포넌트보다 오래 살아야 하나? 이 로직을 React 밖에서도 실행하거나 테스트해야 하나?

> 예: 채팅창을 닫을 때 그 안에서 만든 문서까지 정리돼 다른 화면이 깨졌다. 문서는 채팅창보다 오래 살아야 해서 수명을 채팅창에서 떼어냈다.

## 2. 많이 반복되는 컴포넌트는 필요한 값만 구독해 리렌더 범위를 좁힌다

원칙: root-cause 4
목록 아이템처럼 여러 개 그려지는 컴포넌트는 리렌더 한 번의 비용이 개수만큼 곱해진다. 큰 상태 객체를 통째로 구독하면 관계없는 변경에도 전부 다시 그려진다. 각 View는 자기가 그리는 데 필요한 값만 구독하게 한다.
렌더 비용은 추측하지 않고 프로파일러로 확인한다.
판정 질문: 이 컴포넌트가 다시 그려지는 원인 중 화면이 실제로 바뀌지 않는 변경이 있나? 프로파일러에서 확인했나?

> 예: "렌더 과다는 근거가 약하다"는 분석에 대해, 반복 그려지는 View가 여러 번 리렌더되며 CPU를 크게 잡는 실측 사례로 반박했다.

## 3. 타이밍은 React나 시스템이 보장하는 시점에 걸고, 그 이상의 추적 체계는 만들지 않는다

원칙: root-cause 5, root-cause 6
`requestAnimationFrame`을 중첩해 "이쯤이면 그려졌겠지"를 기다리는 건 운에 맡기는 것이다. 커밋 이후, effect 실행 시점, 브라우저가 보고하는 이벤트처럼 보장된 시점에 건다.
반대로 그 시점을 잡겠다고 Context로 완료 상태를 추적하는 체계를 새로 만드는 것도 과하다. 최악의 경우가 무엇인지부터 정하고, 그걸 막는 데 필요한 만큼만 둔다.
판정 질문: 이 타이밍이 보장된 시점에 걸려 있나, 프레임 수에 걸려 있나? 이 추적 장치를 빼면 막지 못하는 최악의 경우가 있나?

## 4. useEffect는 렌더링 밖의 side effect에만 쓰고, 무거워지면 책임이 잘못 왔는지 의심한다

원칙: type-modeling 4, cohesion 1
effect는 구독, 외부 API 호출, DOM 직접 조작처럼 렌더링만으로는 할 수 없는 외부와의 동기화에 쓴다. props나 다른 상태로 계산되는 값은 렌더 중에 계산하고, 사용자 행동에 대한 반응은 이벤트 핸들러에 둔다. effect로 상태를 맞추면 틀린 값으로 한 번 그린 뒤 다시 그리고, 동기화를 빠뜨린 경로가 생긴다.
effect가 길어지거나 의존성 배열이 계속 늘면 effect가 맡지 말아야 할 책임을 떠안은 신호다. 이벤트 핸들러, React 밖 모듈, 이름 있는 커스텀 훅 중 어디로 갈 일인지 가른다.
판정 질문: 이 effect를 지우면 렌더링 밖의 무엇이 동기화되지 않나? 서로 다른 이유로 다시 실행돼야 하는 일을 한 effect가 여럿 들고 있나?

## 5. 컴포넌트 하나는 바뀌는 이유가 하나가 되게 나눈다

원칙: cohesion 1, abstraction 6
데이터 가져오기, 상태 관리, 상호작용 처리, 레이아웃이 한 컴포넌트에 모이면 그중 하나를 고칠 때 나머지를 다 읽어야 하고, props와 effect가 관심사별로 뒤섞인다. 바뀌는 이유별로 컴포넌트나 훅을 나눈다.
반대로 바뀌는 이유가 같은 몇 줄을 작은 컴포넌트로 잘게 쪼개 위아래로 오가게 만들지는 않는다.
판정 질문: 이 컴포넌트가 바뀌는 이유를 세면 몇 개인가? props와 state가 서로 무관한 묶음으로 나뉘나?

## 6. 연속 상호작용이 끊기면 레이어 합성, reflow와 repaint, 프레임 스케줄링부터 점검한다

원칙: root-cause 4
드래그나 연속 이동에서 프레임이 떨어지는 원인은 대개 매 프레임 레이아웃을 다시 계산하거나, 합성 레이어에서 처리될 변경을 메인 스레드에서 처리하는 데 있다. 위치 변경이 transform으로 처리되는지, 레이아웃을 읽고 쓰는 일이 번갈아 일어나지 않는지, 갱신이 프레임 단위로 묶이는지 본다.
판정 질문: 이 상호작용 중에 레이아웃 재계산이 매 프레임 일어나나? 메인 스레드를 막는 작업이 같은 프레임에 섞여 있나?

## 위반 신호

- 화면보다 오래 살아야 할 상태를 cleanup effect가 지운다. 또는 화면과 함께 사라져야 할 상태가 전역에 남는다
- React 밖에서도 쓰이는 규칙이 컴포넌트, 훅, reducer 안에 있다
- 여러 개 그려지는 컴포넌트가 큰 상태 객체를 통째로 구독한다
- `requestAnimationFrame` 안에 또 `requestAnimationFrame`이 있다
- effect 안에서 setState로 파생 값을 맞추거나, 사용자 행동에 대한 처리를 effect로 한다
- 여러 일을 하는 긴 effect, 계속 늘어나는 의존성 배열
- 데이터 패칭, 상태 관리, 상호작용, 레이아웃이 한 컴포넌트에 섞여 있다. 또는 바뀌는 이유가 같은 코드가 작은 컴포넌트 여러 개로 흩어져 있다
- 드래그 중 `top`, `left`로 위치를 바꾸거나, 레이아웃 값을 매 프레임 읽고 쓴다
