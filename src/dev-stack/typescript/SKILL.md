# TypeScript

타입을 안전하고 깔끔하게 두려면 TypeScript에서 무엇을 쓰고 무엇을 피하나.
원칙 자체는 링크한 dev-core 스킬이 가진다. 여기는 TypeScript에서의 구현과 함정만 둔다. 레포의 컴파일러 설정과 기존 관례를 먼저 따른다.

## 1. optional을 주렁주렁 달지 않고, 케이스는 판별 유니온으로 좁힌다

원칙: type-modeling 1, 7
"어떤 경우에만 있는 필드"를 optional로 달면 타입은 모든 조합을 허용하고, 쓰는 쪽마다 `?.`와 `!`로 어느 경우인지 다시 추측한다. 기능이 늘 때마다 optional이 하나씩 붙어 타입이 무엇을 보장하는지 알 수 없게 된다.
케이스가 갈리면 공통 판별 필드(`kind` 등)로 나누고 각 케이스의 필드는 required로 둔다. optional은 생략해도 의미가 같은 진짜 선택 입력에만 쓴다. switch의 default에서 `never`를 받아 새 케이스를 빠뜨리면 컴파일이 깨지게 하고, 외부에서 예상 밖 값이 올 수 있으면 런타임 throw는 따로 남긴다.
판정 질문: 이 optional 필드가 있을 때와 없을 때가 서로 다른 케이스를 뜻하나? 함께 있거나 함께 없는 optional 필드 묶음이 있나?

> 예: `{ success?: boolean; data?: T; error?: string }`를 `{ kind: "ok"; data: T } | { kind: "error"; error: string }`로 나누니 분기 안의 `!`가 사라졌다.

## 2. 반환 타입은 추론에 맡기고, 각 variant는 satisfies로 검사한다

원칙: type-modeling 2, 3
반환 타입을 넓은 타입으로 적으면 호출자가 받을 수 있는 구체적인 variant가 지워진다. 내부 함수는 추론에 맡기고, 도메인 타입과 맞는지는 반환 값마다 `satisfies`로 검사한다.
반환 타입을 명시하는 건 공개 API 계약을 고정할 때, 재귀 추론이 끊길 때뿐이다.
판정 질문: 반환 타입 표기 때문에 호출자가 알 수 있던 variant가 넓은 타입으로 뭉개졌나?

## 3. 외부 데이터는 unknown으로 받아 경계에서 parse하고, 검증된 타입을 돌려준다

원칙: module-boundaries 5
JSON, 메시지, 설정, 환경변수, 저장소에서 읽은 값은 `unknown`이다. 경계에서 레포의 스키마 라이브러리로 parse해 도메인 타입을 돌려주고, 안쪽 함수는 그 타입만 받는다.
validation만 하고 결과를 버리면 안쪽에서 같은 검사가 반복된다. `Record<string, unknown>`은 parse 입력이지 내부 모델이 아니다.
판정 질문: 외부 값이 parse 없이 단언으로 도메인 타입이 되나? 안쪽 함수가 같은 필드 검사를 또 하나?

## 4. 타입 단언은 탈출구로만 쓰고, type predicate는 주장하는 것을 전부 검사한다

원칙: type-modeling 1
`as any`, `as unknown as T`, `as never`는 컴파일러의 검사를 끄는 것이다. 불가피한 `as T`는 증명할 수 없는 불변식이 있는 가장 좁은 경계에 하나만 두고, 이유를 남긴다.
`x is T`를 반환하는 함수는 컴파일러가 무조건 믿는다. 일부만 검사하는 predicate는 단언보다 위험하다.
판정 질문: 단언을 없애려면 타입이 어떤 규칙을 더 표현해야 하나? predicate의 런타임 검사가 선언한 타입 전체를 확인하나?

> 예: 값이 틀린 모양으로 들어와 소비 직전에 `as`를 붙이자는 안이 왔다. 단언 위치를 옮기는 대신, 값을 만드는 쪽이 처음부터 올바른 타입을 들고 있게 고쳤다.

## 5. 원시값이 섞이면 실제 사고가 날 때만 브랜드 타입을 쓰고, 생성할 때 검증한다

원칙: type-modeling 1
서로 다른 ID 두 종류처럼 바꿔 넣으면 버그가 되는 원시값에만 브랜드를 붙인다. 브랜드 값은 검증하는 생성 함수로만 만든다.
타입이 증명하는 것만 믿는다. 비어 있지 않은 튜플은 첫 원소의 존재를 증명하지만, 임의 인덱스나 숫자의 범위까지 증명하지는 않는다.
판정 질문: 이 브랜드는 실제로 섞일 수 있는 값을 막나? 검증 없이 단언으로 브랜드 값을 만드는 곳이 있나?

## 6. 타입은 원본에서 파생하고, 모양을 다시 적지 않는다

원칙: module-boundaries 6
생성된 타입, 스키마, 상수 객체가 있으면 `Pick`, `Omit`, `ReturnType`, `typeof`, 스키마의 추론 타입으로 끌어온다. 같은 모양을 손으로 다시 적으면 원본이 바뀔 때 소리 없이 어긋난다.
판정 질문: 이 타입 정의를 원본에서 파생할 수 없나? 원본 필드가 바뀌면 이 타입도 컴파일 에러로 같이 깨지나?

> 예: props 타입이 데이터 스키마와 따로 정의돼 있어 스키마가 바뀔 때마다 어긋났다. 모든 props 타입이 스키마 하나를 바라보게 했다.

## 7. 값을 만드는 식으로 쓰고, 없음과 빈 값을 구분한다

원칙: type-modeling 2, abstraction 6
`let`에 여러 분기에서 값을 대입하는 대신 early return이나 값을 내는 분기로 쓴다. 배열과 객체 변환은 `map`, `filter`, `Map`, `Set` 같은 내장 연산으로 표현한다. 읽기 어려운 `reduce`보다 반복문이 낫다.
기본값은 `??`로 준다. `||`는 `0`, `""`, `false`를 없음으로 뭉갠다.
판정 질문: `||` 기본값이 정상 값인 `0`이나 빈 문자열을 덮어쓰나? 재대입되는 `let`을 값을 내는 식으로 바꿀 수 있나?

## 위반 신호

- `as any`, `as unknown as T`, 단언을 두 번 겹친 것, 검사 없이 `true`를 돌려주는 type predicate
- 기능마다 optional 필드가 붙어 자란 타입, 쓰는 곳마다 반복되는 `?.`와 `!`
- optional 필드와 boolean으로 케이스를 가르는 결과 타입, `never` 체크가 없는 switch
- 외부 응답 타입이 parse 없이 안쪽까지 그대로 쓰인다
- 내부 함수에 넓은 반환 타입 표기가 붙어 variant가 지워진다
- 생성 타입과 같은 모양을 손으로 다시 적은 인터페이스
- 숫자나 문자열 기본값을 `||`로 준다
