# 테스트 코드 작성 가이드

## 핵심 원칙

좋은 테스트는 모듈의 **계약(인터페이스)을 명세처럼 기술**한다.  
구현이 바뀌어도 계약이 바뀌지 않으면 테스트는 살아남아야 한다.

---

## Step 1 — 테스트 작성 전: 테스트 가능성 점검

다음 신호 중 하나라도 해당하면 **설계 피드백 신호**다.  
테스트를 바로 작성하기 전에 사용자에게 알린다:

> "이 모듈은 아래 이유로 테스트 작성이 어렵습니다. 설계를 개선 후 작성할까요, 현재 구조로 진행할까요?"

| 신호 | 설명 |
|---|---|
| Observable output 없음 | void-only, getter 없음, 반환값 없음 → 결과를 읽을 방법이 없다 |
| 숨겨진 전제조건 | 호출 조건이 인터페이스에 드러나지 않음 (특정 상태여야만 동작하는 setter 등) |
| Silent failure | warn + return. throw도 없고, 상태 변화도 관찰 불가 |
| Mock 없이 검증 불가 | 계약이 아닌 구현을 테스트할 수밖에 없는 구조 |

> 테스트 가능성과 설계 품질은 같은 신호를 발신한다 — Michael Feathers, [The Deep Synergy Between Testability and Good Design](https://www.youtube.com/watch?v=4cVZvoFGJTU)

---

## Step 2 — 테스트 작성 규칙

### 해야 할 것

**1. 테스트 대상 모듈의 책임만 검증한다**  
협력 모듈, 외부 라이브러리의 동작은 검증하지 않는다. 그 동작은 해당 모듈의 테스트에서 다뤄야 한다.

**2. 코드 경로가 다르면 별도로 테스트한다**  
같은 결과라도 내부에서 다른 경로를 타면 각각 테스트한다. 하나가 통과해도 다른 하나의 버그를 잡지 못한다.
상태기계는 상태 × 입력의 표로 케이스를 세운다. 표에 빈 칸이 많으면 상태가 플래그 조합에 숨어 있는 것이다 (type-modeling 7).

**3. 테스트 이름은 동작(WHAT)을 기술한다 — 구현(HOW)이 아니라**  
구현 방식이 이름에 들어가면 구현이 바뀔 때 이름도 바꿔야 한다.
- ❌ `'변환 배율 100을 곱해 두께를 반환한다'`
- ✅ `'두께를 0~100 범위 값으로 반환한다'`

**4. Assertion은 의도가 드러나는 방식으로 작성한다**  
실패했을 때 원인이 명확해야 한다. 내부 구조에 직접 접근하면 의도가 숨겨진다.
- ❌ `expect(fn.mock.calls[0]?.[0].params.id).toEqual('x')`
- ✅ `expect(fn).toHaveBeenCalledWith(expect.objectContaining({ params: expect.objectContaining({ id: 'x' }) }))`

**5. 반환값이 없는 동작은 외부로 나가는 호출을 검증한다**  
void 함수는 외부 경계(커맨드 버스, 이벤트, API)로 나가는 호출이 올바른지 검증한다.

**6. 테스트 픽스처는 공유한다**  
여러 테스트에서 동일한 setup이 필요하면 test-support 파일로 분리한다. 중복 픽스처는 변경 시 누락을 만든다.

**7. mock 데이터는 테스트 의도를 드러내도록 구성한다**  
mock 값이 검증 대상과 연결되어야 한다. 임의적으로 보이는 값은 독자가 의도를 파악하기 어렵다.

---

### 하지 말아야 할 것

**인프라 코드(구독, 이벤트 리스너 정리)를 기능 모듈 테스트에서 검증하지 않는다**  
모든 모듈 테스트마다 중복된다. 해당 인프라 모듈의 테스트에서 한 번만 다룬다.

**실행 순서에 의존하는 테스트를 작성하지 않는다**  
`beforeEach`에서 `vi.clearAllMocks()`를 호출해 테스트 간 상태를 격리한다.

**`vi.mock()`을 테스트 파일 외부에서 작성하지 않는다**  
호이스팅 제약으로 인해 반드시 테스트 파일 내에서 직접 선언해야 한다.

## 🚩 Red Flags — 이 생각이 들면 멈춰라

| 합리화 | 실제 의미 |
|---|---|
| "Mock이 더 격리된 테스트다" / "호출 여부·횟수가 동작이다" / "내부 구조 직접 접근이 더 간단하다" | 전부 구현 세부사항. 상태나 반환값으로 검증해야 한다 |
| "이 동작도 여기서 같이 검증하면 편리하다" | 다른 모듈의 책임. 해당 모듈 테스트에서 다뤄야 한다 |
| "HOW를 이름에 넣으면 더 명확하다" | 구현이 바뀌면 이름도 바꿔야 함. WHAT으로 충분하다 |
| "두 케이스 결과가 같으니 하나로 합쳐도 된다" | 코드 경로가 다르면 별도 테스트. 하나가 다른 버그를 가린다 |
| "console.warn / 로그도 계약의 일부다" | 상태 변화 없음이 진짜 계약. 문자열 검증은 유지보수 비용 > 가치 |
