# 변경 범위

이 변경을 어디까지, 어떤 순서로, 무엇을 안전장치로 두고 넣을까.
뿌리: 먼저 "꼭 필요해?"를 묻는다. 구조와 엄격함은 필요가 보일 때 더하고, 버릴 코드인지 오래 갈 코드인지에 맞춘다. 이건 기본값이지 자동 규칙이 아니다.

## 1. 요청한 것의 핵심만 남긴다

없어도 결과가 같은 수정이나 덤으로 얹은 코드는 리뷰할 양만 늘린다. 내 관할이 아닌 곳을 고치면 남의 작업을 흔든다. 한 입력에 너무 fit하게 맞춘 조정은 다른 입력에선 효과가 없다.
판정 질문: diff의 각 변경을 빼도 요청한 결과가 같지 않아? 이 조정이 다른 입력에서도 효과가 있는지 확인했어?

> 예: 레이아웃 버그를 고치면서 샘플 하나에 맞춰 크기 값을 조정했다. 다른 입력에선 효과가 없어서 되돌렸다.

## 2. 같은 결함은 다른 곳에서도 찾되, 이번 변경엔 증거가 있는 곳만 넣는다

같은 원인은 보통 다른 경로에도 있다. 한 곳만 고치면 나머지는 그대로 남는다. 그렇다고 확인하지 않은 곳까지 섞으면 이 변경이 무엇을 고치는지 흐려진다.
판정 질문: 같은 코드 경로를 타는 곳을 검색해 봤어? 같이 고친 곳마다 재현이나 코드 경로로 같은 결함이라는 근거가 있어?

> 예: 한 곳의 드래그 취소 버그를 고치면서, 같은 드래그 처리를 쓰는 세 곳도 같이 고쳤다.

## 3. 새로 만들기 전에 기존 방식을 찾고 그 모양에 맞춘다

이미 퍼진 패턴을 한 곳만 바꾸면 같은 문제를 푸는 방식이 둘로 갈린다. 컨벤션이 확고하지 않으면 코드는 금방 중구난방이 된다.
새 방식은 전체로 넓힐 계획이 있을 때 시작한다. 기존 방식에 구조적 문제가 있어서 새로 가는 거라면 그 이유를 분명히 남긴다. 중복은 나중에 일괄 수정하기 쉬운 같은 모양일 때만 둔다.
판정 질문: 같은 일을 하는 코드를 검색해 봤어? 기존과 다른 모양으로 간다면 전체를 옮길 계획과 이유가 남아 있어?

> 예: 같은 껍데기 코드가 이미 17곳에 인라인으로 있는데, 새로 만든 3곳만 공용 모듈로 뽑으려 했다. 패턴이 둘로 갈려서 인라인으로 되돌렸다.

## 4. 근본 수정이 지금 하기엔 너무 크면, 문제가 심한 곳만 고치고 타협한 자리를 드러낸다

전부 못 고칠 때 현재 변경을 보존하는 건 괜찮다. 대신 다음 사람이 이게 타협이라는 걸 알고 걷어낼 수 있어야 한다.
임시 조치에는 임시라고 이름 붙이고, 근본 작업은 할 일로 남긴다. 테스트를 건너뛸 때도 똑같이 표시하고 후속을 남긴다.
판정 질문: 코드만 보고 여기가 임시라는 걸 알 수 있어? 알려진 한계와 후속 작업이 어딘가에 남아 있어?

> 예: 레이어 분리가 선행 작업에 막혀 있었다. 상위 정책에 강하게 묶인 코드를 의도적으로 한 모듈에 모으고, 임시라는 게 드러나게 이름을 붙였다.

## 5. 큰 전환은 additive change로 시작하고, 새 API 제공과 consumer migration을 나눈다

모든 consumer를 한 번에 바꾸게 하는 breaking change는 실패하면 blast radius가 넓고 rollback도 어렵다. 기존 API는 살린 채 새 API를 더하고, consumer는 점진적으로 옮긴다.
이름이나 형식, 의미를 갑자기 바꾸면 그 값에 기대던 consumer가 소리 없이 깨진다. 지표나 저장된 데이터처럼 바깥에서 읽는 값이면 더 그렇다. backward compatibility를 먼저 확인한다.
판정 질문: 기존 API 제거와 consumer migration이 같은 변경에 들어 있지 않아? 바꾼 뒤에도 기존 consumer와 이미 저장된 데이터가 그대로 읽혀?

> 예: 새 기반으로 옮길 때 첫 변경은 더하기만 했다. 기존 설정 함수는 남기고 새 API만 추가했고, 저장 형식에 묶인 필드는 다음 단계로 미뤘다.

## 6. 잘못되면 바로 장애인 변경은 위험부터 확인하고, feature flag나 revert 하나로 되돌릴 수 있게 한다

장애로 바로 이어지는 곳, 되돌릴 수 없는 작업, 남과 같이 쓰는 환경이 여기 든다. 이런 변경은 잘못되면 나 혼자 복구하지 못한다.
그래서 feature flag로 끌 수 있거나 revert 하나로 rollback할 수 있어야 한다. 영향받는 사람에게는 미리 공유한다.
판정 질문: 잘못되면 몇 단계 만에 되돌릴 수 있어? 남의 작업이나 공유 자원에 닿는다면 위험을 먼저 확인하고 공유했어?

> 예: 공용 모듈 전반에 닿는 대기 로직을 바꾸면서, remote flag로 그 환경에서만 끌 수 있게 했다. 적용은 커밋 하나로 얹어 revert 한 번으로 돌아가게 했다.

## 7. 엄격함은 버릴 코드인지 오래 갈 코드인지에 맞춘다

방향 확인이 목적인 PoC에 운영 수준의 저장소나 인프라까지 갖추면 확인만 늦어진다. 반대로 오래 갈 핵심 코드를 PoC처럼 다루면 비용이 나중에 돌아온다.
방향이 불확실하면 큰 결정 전에 최소 범위 PoC로 먼저 확인한다. PoC가 오래 갈 코드로 올라오면 기준도 같이 올라간다.
판정 질문: 이건 버릴 코드야, 오래 갈 코드야? 지금 들이는 추상화나 테스트, 인프라가 그 수명과 영향 범위에 맞아?

> 예: 같은 날, 실험용 저장소에서는 하위 라이브러리를 바로 고쳐 가능성만 봤다. 제품 쪽에는 실제로 운영할 내용만 남겼다.

## 위반 신호

- 요청과 상관없는 파일, 포맷, 이름 변경이 diff에 섞여 있다
- 지적받은 한 곳만 고쳤고 같은 경로를 타는 곳은 그대로다. 또는 근거 없이 여러 곳을 한꺼번에 바꿨다
- 이미 있는 코드와 비슷한 것을 새로 만들었다. 선례와 다른 모양이 한 곳에만 생겼다
- 우회하거나 테스트를 건너뛴 자리에 임시 표시도 후속 작업도 없다
- 기존 API를 지우면서 같은 변경에서 consumer를 전부 옮겼다. 지표 이름이나 저장 필드의 의미가 바뀌었다
- 공유 환경에 닿는 변경인데 끌 flag가 없다. 되돌리려면 커밋 여러 개를 골라내야 한다
- PoC 코드에 운영 수준 인프라가 붙어 있다. 또는 오래 갈 코드가 PoC 수준 검증만 거치고 들어온다
