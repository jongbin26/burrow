# 모듈 경계

이 코드를 어느 레이어에 두고, 책임 경계를 어디에 긋는가.
뿌리: 그 사실을 아는 쪽이 책임진다. 모르는 쪽으로 지식이 새거나 책임이 밀려오면 결함이다.

## 1. 하위 모듈은 consumer의 도메인을 모른다

하위 모듈이 특정 consumer의 도메인 용어나 정책을 알면 재사용성이 깨진다.
하위 모듈은 범용 인터페이스를 제공하고, 그걸 조합해 도메인에 맞게 쓰는 건 consumer의 책임이다.
기능 하나가 쓰던 코드를 공용으로 내릴 때도 같다. 처음 쓴 기능의 이름과 타입을 그대로 내리면 그 기능의 도메인이 공용 모듈에 남는다. 내릴 때 공용 모듈 자신의 도메인 말로 이름과 계약을 다시 짓는다.
판정 질문: 하위 모듈의 이름이나 타입, 분기에 특정 consumer의 도메인 용어가 보이나? 다른 consumer가 그대로 재사용할 수 있나?

> 예: 공용 모듈이 "호출한 기능 → 에러 분류" 매핑을 들고 있었다. 매핑을 걷어내고 호출하는 쪽이 분류를 넘기게 했다.

## 2. producer가 할 일을 consumer가 메우지 않게 한다

consumer에 producer의 결과를 보정하거나 후처리하는 로직이 생겼다면 producer의 책임이 consumer로 밀려온 것이다. producer가 해야 할 정리를 consumer가 대신 호출하는 것도 같다.
보정 위치를 옮기는 걸로 끝내지 않는다. producer가 처음부터 올바른 결과를 내놓게 고친다.
판정 질문: 이 보정이나 후처리를 producer로 옮기면 consumer 코드가 사라지나? 같은 보정이 다른 consumer에도 반복돼 있나?

> 예: 한 객체가 크기를 틀리게 들고 있어서 그 값을 쓰는 두 곳에 각각 보정 로직이 생겼다. 생성 시점에 값을 확정해 두 보정을 지웠다.

## 3. 인터페이스는 consumer가 알아야 할 것만 노출하고, export 목록은 도구로 고정한다

내부 타입이나 호출 순서, 저장 방식 같은 구현 상세가 시그니처로 새면 모든 consumer가 그 상세에 결합된다.
같은 목적의 진입점이 둘이면 consumer는 어느 걸 써야 할지 헷갈린다.
패키지의 public API는 엔트리 파일이 export하는 이름 목록이다. 필요할 때마다 하나씩 export를 늘리면 내부 타입과 내부 캐시가 하나씩 계약이 되고, 결국 내부를 고칠 때마다 consumer가 깨진다.
그래서 export 목록을 allowlist로 다룬다. 목록을 고정하는 테스트와 deep import를 막는 lint를 두어, export를 늘리는 diff는 실패한 뒤 리뷰를 거쳐야 들어오게 한다.
consumer 종류가 다르면(외부 사용처와, 같은 시스템의 다른 레이어) 엔트리를 따로 둔다. 외부용 타입은 내부 타입과 모양이 같아도 따로 선언하고, 내부 타입을 re-export하지 않는다.
판정 질문: 이걸 쓰려면 내부 타입이나 "먼저 이걸 호출해야 한다"는 순서를 알아야 하나? export를 하나 더하는 diff가 테스트나 lint 실패 없이 들어올 수 있나?

> 예: 보관된 리소스를 조회하면 not found가 와서 모든 consumer가 "복구 먼저 호출"을 알아야 했다. 저장 최적화가 조회 계약으로 샌 것이다.
> 감싸는 진입점 하나에서 흡수해 consumer는 그대로 뒀다.

## 4. 변경 주기가 같은 것끼리 묶고, 의존은 단방향으로 둔다

레이어는 변경 주기가 같은 것끼리 모으려고 나눈다. 컨벤션만 보고 쪼개면 변경 하나가 여러 레이어로 번진다.
조립 레이어는 모듈 간 연결만 맡는다. 조립 레이어에 특정 기능의 로직이 쌓이면 모듈을 하나 더 분리해야 한다는 신호다.
실행 환경처럼 바뀌는 것은 진입 경계에서 구현체를 주입한다. 코어는 자기가 어느 환경에서 도는지 몰라야 한다.
판정 질문: 한 기능을 고쳤는데 다른 모듈이나 조립 레이어까지 고쳐야 하나? 실행 환경을 바꾸면 코어 코드가 바뀌나?

> 예: "A 작업이 끝나면 B 버튼 상태를 바꾼다"는 요구에서 두 버튼은 각자 모듈에 둔다. 완료 상태만 조립 레이어가 들고 주입한다.

## 5. 외부 데이터는 최외곽에서 validation하고 도메인 모델로 변환한다

외부 응답 스키마를 안쪽 레이어까지 그대로 쓰면 내부 코드가 외부 스펙에 결합되고, 곳곳에 null 체크와 타입 단언이 생긴다.
외부 데이터는 모듈 최외곽에서 validation하고 도메인 모델로 변환한다. 안쪽 레이어는 도메인 모델만 안다.
변환이 여러 단계면 단계마다 입력과 출력 스키마가 분명해야 하고, 순수 변환에 다른 로직을 섞지 않는다.
판정 질문: 안쪽 레이어가 외부 응답 타입을 직접 참조하나? 각 변환 단계의 입출력 스키마를 말할 수 있나?

## 6. single source of truth를 두고, 호출 순서 같은 규칙은 구조가 강제하게 한다

손으로 동기화하는 목록이나 사본, "A를 호출한 다음 B를 호출해야 한다" 같은 관례는 정책을 사람의 기억에 맡긴 상태다. 규칙을 모르는 사람이 고치면 조용히 틀린다.
같은 사실은 한 곳에만 정의하고 나머지는 거기서 참조한다. 순서나 누락은 빼먹을 수 없는 API 구조로 막는다.
판정 질문: 이걸 바꾸려면 몇 곳을 고쳐야 하지? 하나를 빼먹으면 장애가 나기 전에 알 수 있나?

> 예: 같은 타입 목록이 세 곳에 하드코딩돼 있었고, 새 타입이 한 곳에서 빠져 차단 규칙이 적용되지 않았다. 목록을 한 곳으로 모아 세 규칙이 참조하게 했다.

## 7. 지금 못 지킨 경계는 한 모듈에 격리하고 이름으로 임시임을 드러낸다

일정이나 합의 때문에 경계를 당장 지킬 수 없을 때가 있다. 그때 결합이 여기저기 흩어지면 나중에 걷어낼 지점을 못 찾는다.
타협한 결합은 한 모듈에 격리하고, 이름부터 "특정 기능 전용, 임시"라고 드러낸다.
판정 질문: 경계를 어긴 코드가 한 모듈에 격리돼 있나? 이름만 보고 제거 대상인 걸 알 수 있나?

## 위반 신호

- 하위 모듈의 타입이나 이름, 분기에 특정 consumer의 도메인 용어가 나온다
- consumer에 producer의 결과를 보정하거나 후처리하는 로직이 있다
- 같은 일을 하는 public 함수가 둘이다. 또는 "먼저 X를 호출해야 한다"는 주석이나 관례가 있다
- public 시그니처에 내부 타입이 나온다. 또는 외부용 타입이 내부 타입을 re-export한 것이다
- 엔트리가 `export *`로 내부 모듈을 통째로 내보낸다. 또는 export 목록을 고정하는 테스트나 deep import를 막는 lint가 없다
- 조립 레이어가 특정 기능의 로직을 직접 들고 있다
- 외부 응답 타입이 안쪽 레이어에서 참조되고, null 체크가 깊게 이어진다
- 같은 목록이나 정의가 여러 파일에 하드코딩돼 있다. 또는 생성된 파일을 직접 고쳤다
- 범용처럼 보이는 이름의 코드가 사실은 한 기능 전용이고, 그런 코드가 여러 곳에 흩어져 있다
- 여러 기능이 쓰는 공용 코드의 이름에 처음 만든 기능의 이름이 남아 있다
