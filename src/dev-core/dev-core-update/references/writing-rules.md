# 개발 지식 스킬 작성 규칙

사용자가 스킬 문서의 표현이나 구성을 지적할 때마다 한 줄씩 쌓는다. 새 규칙을 넣으면 적용되는 모든 스킬을 다시 점검한다.
1~11번은 dev-core 와 dev-stack 모두에 적용한다. 단 1번과 8번은 dev-core 에만 적용하고, dev-stack 은 아래 "dev-stack 규칙"을 따른다.

1. 특정 언어, 프레임워크, 라이브러리에 바인딩되지 않은 범용 지시로 쓴다. 다른 스택의 레포에서 처음 읽은 에이전트도 판정할 수 있어야 한다 (가장 우선)
2. 범용 개발 용어는 그대로 쓴다. validation, 레이어, 책임 경계, lifecycle, consumer 같은 말을 억지로 우리말로 풀지 않는다
3. 특정 사례가 원칙의 주 내용이 되지 않게 한다. 원칙 제목과 판정 질문은 여러 사례에 공통된 개념으로 쓰고, 사례는 `> 예:` 블록으로 내린다. 근거가 한 건인 사례에 원칙의 비중을 나눠 주지 않는다
4. 대화 속 특정 장면에서 나온 구절을 그대로 옮기지 않는다. 사용자 표현 중 개념을 담은 말("책임이 밀려왔다", "땜빵 위의 땜빵")은 쓰고, 장면이나 API에 묶인 말은 일반화한다
5. 너무 세부적인 내용은 쓰지 않는다. 예시는 원칙마다 하나, 3줄 이내로 일부만 허용한다
6. 원칙 제목은 한 문장, 판정 질문은 두 개 이하로 쓴다. 에이전트가 기준을 하나로 잡을 수 있어야 한다
7. 사람이 읽기 쉽게 쓴다. 한자어 명사를 나열한 압축어를 풀고, 한 문장에 생각 하나만 담는다
8. 고유명사를 쓰지 않는다. 프로젝트명, 제품명, 사내 시스템, 클래스명이 여기에 해당한다
9. 판정 질문은 에이전트가 코드나 diff를 보고 답할 수 있는 형태로 쓴다. "쭉 읽히나"처럼 감으로 답하는 질문 대신 "사용처를 찾아봤을 때", "인라인하면"처럼 확인 행동을 담는다. 예외 조항은 근거를 코드나 문서에서 가리킬 수 있을 때만 열어 둔다
10. 예시는 산문보다 두 줄 안팎의 타입·시그니처 스케치가 낫다. 식별자는 범용 개발 어휘(drag·hover·cache·undo)만 쓰고, 그 레포에만 있는 이름과 개수·줄 수는 뺀다. 판정: 다른 스택의 사람이 자기 코드에서 같은 모양을 찾을 수 있나
11. 특정 도메인이나 제품에서 나온 판단을 기술 전반의 규칙으로 올리지 않는다. 그 판단이 성립한 조건(상태의 수명, 사용 범위, 규모)을 찾아 조건부 규칙으로 쓰고, 반대 조건에서는 어떻게 하는지도 함께 쓴다. 판정: 같은 기술을 다른 종류의 앱에 쓰는 사람에게도 이 규칙이 맞나

## dev-stack 규칙

- 그 기술의 이름, API, 짧은 코드는 쓴다. 다만 버전마다 이름이 다른 API는 본문에 박지 않고, 버전을 확인할 곳을 적는다
- 원칙마다 `원칙:` 줄로 대응하는 dev-core 원칙을 링크하고, 원칙 자체를 다시 설명하지 않는다
- 공식 문서나 이미 설치된 다른 스킬이 다루는 일반론은 옮기지 않는다. 그 기술에서 사용자가 다르게 판단하는 지점만 둔다
