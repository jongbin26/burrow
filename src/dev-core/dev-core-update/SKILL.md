# 개발 지식 갱신

이 대화에서 나온 판단을 개발 지식 스킬에 넣는다. 어느 스킬의 어느 원칙에, 어떤 문장으로 넣을지 정하는 게 이 절차의 일이다.
대상은 `src/dev-core/` 아래 스킬뿐이다. PR, 커밋, AI 활용처럼 개발 지식이 아닌 규칙은 `global-skill`로 보낸다.

## 1. 레포를 찾고 원격과 맞춘다

```sh
REPO=$(dirname "$(dirname "$(readlink "$HOME/.codex/AGENTS.md" 2>/dev/null || readlink "$HOME/.claude/CLAUDE.md")")")
git -C "$REPO" status --short
git -C "$REPO" pull --ff-only
```

- `$REPO/manifest.txt` 가 없으면 아직 세팅 전이다. 알리고 멈춘다
- 작업 트리에 변경이 남아 있으면 pull 하지 않는다. 변경 목록을 보여주고 진행할지 묻는다
- pull 이 fast-forward 로 안 되면 멈추고 알린다

## 2. 대화에서 후보를 뽑는다

사용자가 직접 말한 곳만 후보다. 후보는 두 종류다.

- 판단 기준: 설계나 구현에 대한 판단, 에이전트 제안을 거부하거나 고쳐 준 곳. 3단계로 간다
- 작성 규칙: 스킬 문서의 표현이나 구성에 대한 지적. `references/writing-rules.md` 에 한 줄로 추가하고, 이미 있는 규칙이면 문장만 보강한다. 그다음 `src/dev-core/` 의 모든 스킬을 그 규칙으로 다시 점검한다

판단 기준 후보마다 세 가지를 적는다.

- 명제: 어느 레포에서든 지켰는지 가릴 수 있는 문장 한 줄
- 근거: 이 대화에서 사용자가 한 말. 고치지 않고 그대로 옮긴다
- 거부한 대안: 있으면 적는다

근거가 에이전트가 쓴 문장뿐이면 후보로 올리지 않는다.

## 3. 넣을 자리를 정한다

`$REPO/src/dev-core/*/SKILL.md` 를 모두 열어 description 과 원칙 제목을 읽는다. 그다음 아래 넷 중 하나를 고른다.

| 결론 | 언제 | 할 일 |
|---|---|---|
| 기존 원칙 보강 | 기존 원칙의 판정 질문으로 그대로 가려진다 | 왜, 판정 질문, 예시 중 모자란 곳만 고친다 |
| 새 원칙 | 스킬이 다루는 질문에는 속하지만 판정 질문이 다르다 | 템플릿 형식으로 추가한다 |
| 새 스킬 | 어느 스킬이 다루는 질문에도 속하지 않는다 | 스킬 경계를 제안하고 사용자 승인을 받는다 |
| 충돌 | 기존 원칙과 반대 방향이다 | 둘을 나란히 보여주고 사용자가 고르게 한다 |

추가하면 원칙이 7개를 넘는 스킬이라면 그냥 넣지 않는다. 합치거나 쪼개는 안을 제안한다.

## 4. 작성 규칙을 지켰는지 본다

스킬에 들어갈 것은 사용자의 유스케이스가 아니라 어느 레포에서든 적용될 규칙이다.
`references/writing-rules.md` 의 규칙을 모두 지킨다. 형식은 `references/template.md` 를 따른다.

## 5. 보여주고 멈춘다

- 바꾼 파일의 diff 를 보여준다. 근거가 된 사용자 원문도 함께 보여준다
- 커밋 메시지 초안을 낸다. 언어는 레포의 기존 커밋을 따른다
- 커밋과 푸시는 사용자가 한다
- 새 스킬을 만들었다면 `$REPO/bin/doctor.sh` 를 돌려 `MISSING` 목록을 보여주고, `bin/link.sh` 를 돌릴지 묻는다. 링크해도 세션을 다시 시작하기 전에는 로드되지 않는다. 이것도 함께 알린다

## 위반 신호

- pull 하지 않고 고쳤다
- 근거가 에이전트 문장뿐인 원칙을 넣었다
- 원칙이나 판정 질문에 특정 기술 어휘나 고유명사가 들어 있다
- 사용자가 문서 작성을 지적했는데 writing-rules.md 에 남기지 않았다
- 기존 원칙과 판정 질문이 같은데 새 원칙으로 따로 넣었다
- 커밋까지 했다
