# 타입 모델링

상태와 결과, 실패와 비동기를 어떤 모양으로 표현할까.
뿌리: 규칙은 사람이 기억하는 게 아니라 구조가 지키게 한다. 모르는 것을 그럴듯한 값으로 메우지 않고, 모른다고 드러낸다.

## 1. 규칙은 타입으로 강제하고, 타입으로 못 막는 자리는 runtime validation이 명시적으로 실패시킨다

optional 필드나 타입 단언, boolean 플래그는 타입이 표현하지 못한 규칙을 사람이 기억하게 만든다. discriminated union으로 케이스를 나누고 필요한 필드를 required로 두면 새 케이스를 빠뜨렸을 때 컴파일러가 잡아 준다.
타입이 너무 복잡해지는 자리는 runtime validation으로 메운다. 이때 validation은 throw하거나 경고를 남기고, 조용히 통과시키지 않는다. 값을 그대로 전달만 하는 경로라면 굳이 엄격한 타입이 필요 없다.
판정 질문: 타입 단언이나 required 값에 대한 방어 코드가 남아 있다면, 타입이 규칙을 덜 표현한 것 아닌가? 타입으로 못 막은 자리의 validation은 실패 시 throw하거나 경고를 남기나?

> 예: validation 결과가 성공 여부와 실패 이유를 모두 optional 필드로 들고 있어, 성공인데도 실패 필드에 접근할 수 있었다.
> 성공과 실패를 discriminated union으로 나누니 분기 안의 단언이 사라졌다.

## 2. "모름", "없음", "고르지 않음"을 같은 값으로 뭉개지 않고, 처리 못 한 것은 결과에 남긴다

default 값이나 fallback, 빈 문자열로 메우면 손실이 성공의 형태로 남아 나중에 아무도 원인을 찾지 못한다. 의미 없는 값을 채워 넣는 건 쓰레기 정보다.
없는 값은 없다고, 버린 것은 버렸다고 결과에 남긴다.
판정 질문: 이 fallback이 실제 값이 맞나? 경고만 남기고 early return하면 호출한 쪽은 성공과 실패 중 무엇을 받나?

> 예: 변환기가 모르는 항목을 건너뛰고 성공을 돌려줬다. 성공 결과에 버린 항목 목록을 같이 담아 호출한 쪽이 알 수 있게 했다.

## 3. 실패는 한 경로로만 흐르게 하고, 예상된 실패는 값으로, 잘못된 사용은 예외로 다룬다

같은 실패를 콜백과 반환값에서 따로 다루면 흐름을 따라가기 어렵고, 한쪽이 빠지면 아무 신호 없이 멈춘다.
취소나 결과 분기처럼 호출한 쪽이 처리할 것은 값으로 반환한다. 잘못된 사용은 조용히 넘기지 않고 바로 throw한다.
판정 질문: 이 실패를 처리하는 곳을 모두 찾으면 한 곳인가? 실패가 결과 흐름에 빠짐없이 전달되나?

> 예: 공용 모듈의 실패가 콜백으로만 전달되고 결과 흐름에는 나오지 않아, 사용처의 로딩 상태가 끝나지 않았다.

## 4. 상태를 하나 더 만들기 전에 이미 있는 값들로 계산할 수 있는지 본다

상태가 하나 늘 때마다 동기화해야 할 짝이 생긴다. 카운터를 올리고 내리는 식의 명령형 코드는 순서가 어긋나면 깨진다. 기존 값에서 derive하면 갱신 경로가 하나로 준다.
판정 질문: 이 상태를 기존 값들로 derive할 수 없나? 이 상태를 갱신하는 곳을 모두 찾으면 여러 곳인가?

## 5. 비동기 도구는 흐름의 모양에 맞춰 고르고, 무엇이 언제 다시 계산되는지 드러낸다

지금까지의 기조는 이렇다. 성공이나 실패로 한 번 끝나는 작업은 단발성 비동기로 충분하고, 스트림은 과하다. 여러 단계를 시간 순으로 거치거나 사용처가 단계마다 상태를 받아야 하면 상태를 내보내는 스트림을 쓰고, 사용처는 구독만 한다. 에러 처리가 여러 곳에 흩어져 한 곳에 모아야 하면 typed error를 다루는 방식을 쓴다.
정해진 규칙은 아니다. 상황에 맞게 고르고, 고른 이유를 남긴다. reactivity를 잘게 쪼갤수록 구독 비용이 드니 어디까지 쪼갤지는 그 비용과 맞바꿔 정한다.
스트림은 "언제 시작하고 언제 끝나나"의 시간 순 결합을 푸는 도구다. "지금 어느 모드인가"의 분기 수는 줄이지 않는다. 분기가 많아 읽기 힘든 코드는 7번의 문제이지 도구의 문제가 아니다.
판정 질문: 함수 하나가 중복 실행 방지, 타이밍 제어, 에러 처리를 명령형으로 다 들고 있지 않나? 재계산을 일으키는 의존성이 명시적으로 선언돼 있나, 함수 안에서 무엇을 읽느냐로 암묵적으로 정해지나?

> 예: 변환 작업이 플래그 두 개와 try/catch로 진행 상태를 관리했다.
> "요청 → 진행 중이면 무시 → 시작 상태와 에러 처리"를 스트림 하나로 표현하고, 사용처는 구독만 하게 했다.

## 7. 플래그 조합이 상태기계면 상태에 이름을 붙이고, 모드는 들어올 때 한 번 정한다

nullable 필드와 boolean 몇 개의 조합이 실제 상태인 코드는, 이벤트마다 그 조합을 다시 해독해 모드를 알아낸다. 같은 해독이 시작·진행·끝 함수에 반복되고, 끝에서 해독하는 함수가 가장 길어진다.
상태를 discriminated union으로 이름 붙이고, 모드는 시작 입력(도구·보조키·대상)에서 한 번 정해 저장한다. 진행과 끝은 그 이름으로 분기해 각자 짧아진다.
판정 질문: 지금 어느 모드인지 알려면 필드를 몇 개 조합해야 하나? 끝나는 이벤트의 함수가 시작 조건을 다시 읽고 있나?

> 예: `drag: { additive, moved } | null` · `corner: Point | null` · `tool`의 조합이 실제로는 상태 여섯 개였다.
> `gesture: idle | marquee | regionDrag | regionCorner | handles`로 이름 붙이자 release는 `switch (gesture.kind)` 하나가 됐다.

## 6. 조회는 상태를 바꾸지 않고, side effect가 있다면 시그니처에 드러낸다

조회가 상태를 바꾸거나 다른 동작을 trigger하면, 그 사실을 모르고 조회를 쓴 사람에게 책임이 밀려온다. 조회는 idempotent해야 한다.
상태 정보는 에러 코드에 숨기지 않고 응답 모델에 담는다. 서버 API 계약에도 같은 잣대를 댄다.
판정 질문: 이 조회를 두 번 호출하면 결과나 상태가 달라지나? 시그니처만 보고 side effect가 있는지 알 수 있나?

> 예: 문서 조회가 곧 복구 요청이었고, 복구 중이라는 상태는 "없음" 에러로만 알 수 있었다. 조회와 복구를 나누고 상태를 응답 필드로 받게 했다.

## 고려할 질문

- 객체로 모델링할지 discriminated union으로 나눌지: 한 연산 안에서 케이스별 세부 필드를 같이 봐야 하나, 공통 인터페이스만 있으면 되나. 판정 기준이 아니라 고려할 질문으로 둔다

## 위반 신호

- 타입 단언, 특히 단언을 두 번 겹친 것
- 기능이 늘 때마다 optional 필드가 붙는 거대한 입력 타입이나 결과 타입
- optional 메서드라서 구현을 빠뜨려도 통과하는 계약
- required 값에 거는 방어 코드
- 경고 로그만 남기고 early return, 빈 catch, 의미가 다른 default 값으로 메우기
- 같은 실패를 콜백과 반환값 양쪽에서 처리하기
- 기존 값으로 derive되는 새 상태, 손으로 올리고 내리는 대기 카운터
- 함수 하나에 중복 실행 방지 플래그, 타이머, 다른 동작 호출이 함께 들어 있음
- 조회 함수 안의 쓰기나 trigger, 이유 없이 비동기를 반환하는 동기 연산
- nullable·boolean 필드 서넛의 조합으로 모드를 가리고, 같은 조합 해독이 여러 함수에 반복됨
