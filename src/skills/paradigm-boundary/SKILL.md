# 패러다임 경계

고른 쪽의 세부 규칙은 `oop` 또는 `functional-programming`에 있다.

## 1. 표현(representation)을 공유해야 하는지로 가른다

| | 객체지향 | ADT (태그드 유니온 + 연산) |
|---|---|---|
| 외부에 보이는 것 | 인터페이스만 | 변형(variant) 전체 |
| 타입을 아는 방법 | 객체 간 메시지 | 같은 연산 안에서 변형 확인 |
| 잘하는 것 | 구현을 감춘 채 교체 | 변형 간 세부 제어 |

- 여러 변형의 **내부 값을 한 자리에서 같이 보고 판단**해야 한다 → ADT
- 상대의 내부를 몰라도 되고 **구현을 갈아끼우는 것**이 목적이다 → 객체지향

객체지향에서는 상대의 내부 표현을 볼 수 없어 표현을 하나로 고정해야 하고, 더 필요하면 public
인터페이스로 노출해 메시지로 받아야 한다.

## 2. 무엇이 자주 늘어나는지로 한 번 더 가른다

- **새 변형이 자주 는다**(결제 수단, 도형 종류) → 객체지향. 변형을 더해도 기존 연산을 안 건드린다
- **새 연산이 자주 는다**(같은 데이터의 새 해석) → ADT. 연산을 더해도 변형을 안 건드린다

## 3. 한쪽으로 끝까지 가거나, 섞는 지점을 경계로 만든다

애매하게 섞이면 읽는 쪽이 두 멘탈 모델을 동시에 굴려야 한다. 섞어야 하면 어댑터·Facade를 두고
**그 안에서만 변환**한다.

## 4. 프론트엔드에서는 교체 지점에만 인터페이스를 연다

React에는 이미 객체지향 장치가 들어 있다 — Context(의존성 역전), 합성, props(위임).
클래스를 더 세우는 것이 곧 객체지향이 아니다. 뷰와 강결합되고 요구사항이 다양해
**인터페이스를 갈아끼울 일 자체가 드물다.**

열어 둘 곳: 런타임에 구현체를 대체해야 하는 지점(외부 API 클라이언트, 장애 시 대체 구현).

## 위반 신호

- 클래스 인스턴스를 만들어 놓고 밖에서 필드를 꺼내 분기한다 (객체지향의 껍데기)
- 순수 변환 파이프라인 중간에 상태를 든 객체가 한 단계만 끼어 있다
- 같은 개념이 어떤 경로에서는 클래스, 어떤 경로에서는 유니온으로 표현된다
- `instanceof` 분기와 `switch (kind)` 분기가 같은 도메인에 함께 있다
- 변형을 하나 추가했는데 연산 여러 곳을 동시에 고쳐야 한다 (축 선택이 틀렸다는 신호)
