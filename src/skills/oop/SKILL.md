# 객체지향

클래스를 쓴다고 객체지향이 아니다. 판정 기준은 문법이 아니라 협력의 모양이다.

## 1. 메시지를 먼저 정하고, 처리할 객체를 나중에 찾는다

- "A는 B에게 **무엇을 시키고 싶은가**"로 출발 — 메서드 시그니처를 먼저 확정
- 송신자는 수신자의 정체가 아니라 **메시지의 형식만** 안다
- 이미 B를 소유했는지는 무관 — 무엇을 묻고 무엇을 시키는지가 갈림길

## 2. 상태를 묻지 말고 시킨다

호출자가 남의 필드를 읽어 분기하면 소유 관계와 무관하게 잘못된 협력이다.

```ts
if (b.stock > 0) { b.stock = b.stock - 1; }   // ❌ 캐묻고 호출자가 판단
b.decrease();                                  // ✅ 책임을 가진 쪽에 위임
```

## 3. 주입할지 직접 생성할지는 세 질문으로 정한다

| 질문 | 판정 |
|---|---|
| A가 B의 내부 상태를 읽고 판단하는가 | 그렇다 → 메시지로 책임 위임 |
| B가 교체될 가능성이 있는가 | 있다 → 인터페이스 주입 / 없다 → 직접 생성 |
| B가 A의 내부 구현 세부사항인가 | 그렇다 → 직접 생성·호출 / 협력자다 → 주입 |

교체 계획이 없는데 인터페이스부터 세우지 않는다. 주입할 때는 **필요한 메서드만 Pick**해 좁게 의존한다.

## 4. 상속은 계약까지 이행할 때만 쓴다

is-A 판정이 어려운 건 시그니처가 아니라 **계약(LSP)**까지 맞춰야 하기 때문이다.

- 확장이 필요하면 부모가 확장점을 계약에 명시한다 (Template Method)
- 계약을 깨는 변경은 상속이 아니라 **위임(delegation)**으로 푼다
- 계약 위반은 컴파일도 되고 값도 반환하지만 틀리고, **오류 위치가 원인 위치와 다르며**,
  특정 데이터 조건에서만 재현된다 — 그래서 인터페이스 위반보다 위험하다

## 5. 타입은 계약으로 쓴다

구현이 지금 좁은 값만 반환해도 **넓은 반환 타입은 설계 의도**다 — 구현 디테일을 호출자에게
노출하지 않겠다는 뜻이다. 선언을 구현에 맞춰 좁히면 타입이 계약이 아니라 구현의 스냅샷이 된다.

## 위반 신호

코드에서 아래가 보이면 위 규칙 중 하나가 깨진 것이다.

- 조건문이 다른 객체의 필드를 읽는다 (`if (other.state === ...)`, `other.list.length`)
- `super.x()` 결과를 받아 덮어쓴 뒤 반환한다
- 부모를 건너뛰고 조부모 구현을 호출해 중간 계층 override가 무시된다
- 구현체가 하나뿐인 인터페이스가 교체 계획 없이 존재한다
- 반환 타입이 구현이 실제로 내놓는 좁은 리터럴로 선언돼 있다
- 생성자가 주입받은 인터페이스의 메서드 중 극히 일부만 쓴다
