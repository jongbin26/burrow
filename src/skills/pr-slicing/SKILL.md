# PR 분할

## 1. PR로 낼지 커밋으로 남길지 먼저 정한다

경계를 긋기 전에, **그 경계가 PR 경계인지 커밋 경계인지**부터 판정한다. 나눌 만한 조각이라는
것과 PR을 따로 낼 조각이라는 것은 다른 판단이다.

조각이 PR을 얻는 조건은 둘 중 하나다.

- **독립된 판정이 필요하다** — 리뷰어가 답해야 할 질문이 앞 조각과 다르다(3번의 성격 차이)
- **독립된 운명이 필요하다** — 앞 조각이 반려·롤백돼도 이 조각은 살아야 하거나, 반대로 이 조각만
  먼저 배송돼야 한다

둘 다 아니면 커밋이다. 같은 리뷰어가 같은 질문에 한 자리에서 답하고 어차피 함께 머지될 조각은
**한 PR 안의 커밋으로 남긴다** — 커밋 단위의 서술은 `pr-writing`이 그대로 적용되므로 조각의
경계와 근거는 커밋 히스토리에 남는다. 잃는 것은 없고 리뷰어가 여는 창의 수만 줄어든다.

사후 판정은 머지 시각이 한다 — **한 번에 머지됐으면 그것은 커밋이었다.** 한 저장소에서 PR 26개를
스택으로 냈고 그중 18개가 커밋 하나짜리였다. 바닥 하나를 뺀 25개가 18초 안에 한 번에 머지됐다 —
어느 하나도 따로 판정되거나 따로 배송되지 않았으므로, 25번의 PR 개설이 산 것이 없다.

## 2. 경계는 전파가 끊기는 지점에 긋는다

한 변경이 다른 부분의 동작 가정을 깨면 그 둘은 한 PR이다. 안 깨면 나눌 수 있는 후보다.
전파 범위는 코드 크기가 아니라 **누가 이 변경 때문에 다시 검토해야 하는가**로 잰다.

의존 방향 자체를 판단하는 기준(레이어·결합도)은 `module-boundaries`.

## 3. 성격이 다른 변경은 같은 PR에 넣지 않는다

기능(사용자 스토리) 단위가 아니라 **변경의 성격** 단위로 쪼갠다. 성격이 다르면 리뷰어가
확인해야 할 질문이 다르다 — 하나의 PR에 섞이면 어느 쪽 질문에도 제대로 답하지 못한다.

- 동작 불변 리팩터 / 동작 변경 기능 추가 — 항상 분리 (동작 불변·변경 구분은 `change-scope`,
  어느 쪽인지 본문에 못박는 것은 `pr-writing`)
- 인터페이스 계약 변경 / 그 계약의 소비처 마이그레이션 — 항상 분리. 계약만 있는 PR이라야
  리뷰어가 계약 자체를 검증할 수 있다
- 신규 구현 추가(아직 아무도 안 씀) / 기존 경로를 신규로 전환 — 분리 가능하면 분리한다

## 4. 의존 구조가 전달 방식을 정한다

**1번 문턱을 넘은 조각들 사이에서만** 전달 방식을 고른다 — 커밋은 스택의 층이 아니다.
변경을 레이어별로 묶고 그룹 간 참조 방향을 먼저 그린다. **의존 구조**(선형·무관·순환)와
**전달 방식**(스택·병렬·직렬)은 다른 축이다.

- 방향이 선형이면(A의 계약 위에 B가 선다) **스택** — B의 base를 A 브랜치로 두고 **바로 열어
  병렬 리뷰**한다. A가 머지되면 B의 base는 자동으로 A의 base로 재지정된다
- 방향이 없으면(서로 다른 모듈, 공유 계약 없음) **병렬** — 순서·base 제약이 없다
- 방향이 순환이면 나눌 수 있는 단위가 아니다 — 한 PR로 남긴다

**직렬(A 머지를 기다려 B를 낸다)은 스택의 대안이 아니라 차선이다.** 쪼갠 개수만큼 리드타임이
곱해져, 분할로 얻은 리뷰 가능성을 배송 지연으로 되물어준다. A의 히스토리가 머지 시점에 재작성되는
전략(squash·rebase 머지)이라 자식 rebase 비용이 분할 이득보다 클 때만 직렬을 고른다.

## 5. 스택 부모는 히스토리를 재작성하지 않는다

부모 브랜치에 force-push(로컬 squash·rebase·amend)를 하면 조상 SHA가 갈려 **자식 전부에
rebase가 강제**된다. 리뷰 반영은 추가 커밋으로 얹고, 정리가 필요하면 스택을 모두 머지한 뒤에 한다.

## 6. 스택 등록은 base 체인과 다른 층이다

base를 앞 브랜치로 두면 스택은 이미 성립하고 병렬 리뷰도 열린다(4). 호스팅 도구의 **스택 등록**은
그 위의 별개 층이다 — 등록해야 얻는 것은 레이어 UI, 스택 단위 일괄 머지, 그리고 부모 머지 시
자식의 자동 rebase·retarget이다(*"when a parent PR merges … the pull requests above it stay open
and automatically rebase and retarget"*). 등록은 선택이며, 등록하지 않았다고 규칙 위반이 아니다.

등록 도구를 쓸 때 두 가지가 조용히 깨진다.

- **트렁크 기본값이 저장소 기본 브랜치다.** 릴리스·핫픽스처럼 트렁크가 기본 브랜치가 아니면
  반드시 명시한다(`--base`). 누락하면 바닥 PR의 base가 경고 없이 기본 브랜치로 바뀐다
- **등록 후에는 base를 못 바꾼다** — `Cannot change the base branch because the pull request is
  part of a stack`. 되돌리려면 등록 해제 → base 수정 → 재등록 순서다

**스택 브랜치의 이름은 바꾸지 않는다.** 호스팅 API의 브랜치 rename은 그 브랜치를 *base로* 쓰는
PR만 새 이름으로 재지정하고, *head로* 쓰는 PR은 닫는다. 이름을 바꿔야 하면 스택을 다 머지한 뒤에 한다.

## 7. 조각은 그 자체로 완결돼야 한다

중간 PR이 빌드나 테스트를 깨뜨린 상태로 머지되면 스택형 분할의 의미가 없다 — 각 PR은
머지 시점에 그 자체로 정합해야 한다. 아직 아무도 안 쓰는 코드도 사용되지 않은 채로 빌드·
타입·테스트를 통과해야 나눌 자격이 있다.

## 8. 나눌 수 없으면 억지로 나누지 않는다

전파가 끊기지 않거나(2) 조각이 그 자체로 완결되지 않으면(7) 하나의 PR로 남긴다. 분할은
리뷰 가능성을 위한 수단이지 목표가 아니다 — 억지로 쪼갠 PR은 각각 봐도 판단이 안 서고
결국 다시 묶어서 리뷰하게 만든다.

## 위반 신호

- 스택 전체가 같은 시각에 한 번에 머지된다
- 스택 안의 PR에 커밋이 하나뿐이고 PR 제목이 그 커밋 메시지와 같다
- 리팩터와 기능 변경이 같은 diff에 섞여 있다
- 인터페이스 시그니처 변경과 그 시그니처를 쓰는 모든 호출부 변경이 한 PR에 있다
- 스택 부모 브랜치에 force-push 이력이 있다
- 선형 의존인데 앞 PR 머지를 기다리느라 뒤 PR이 열리지 않은 채 대기 중이다
- 스택 자식 PR이 부모 미머지 상태에서 빌드가 깨져 있다
- 스택 바닥 PR의 base가 의도한 트렁크가 아니다
- 스택에 속한 브랜치를 rename해 PR이 닫혔다
- "이 PR만 보면 뭘 검증해야 할지 모르겠다"는 리뷰 코멘트가 반복된다
- 병렬로 낸 PR 두 개가 같은 계약 파일을 동시에 고친다
