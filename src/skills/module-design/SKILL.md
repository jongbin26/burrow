# 모듈 설계

## 1. 판단 질문은 "고칠 때 변경이 어디까지 흘러가나"

"이 코드가 여기 있어도 되나"보다 낫다. 선을 어디에 긋느냐가 다음 변경의 범위를 정한다.

모듈성은 **높은 응집도와 낮은 결합도**라는 속성이지 크기가 아니다. 함수·클래스·파일·패키지가
각자의 층위에서 모듈이고, 경계도 층위마다 있다. **파일을 나눈 개수는 경계가 아니다** — 나눈 뒤에도
변경이 서로에게 흘러가면(순환 참조) 가짜 추상화다.

둘 곳을 정한 뒤 **그 안을 클래스로 모델링할지 태그드 유니온으로 모델링할지**는 `paradigm-boundary`.

## 2. 의존은 한 방향으로, 기준은 변경 빈도

**변하기 쉬운 것이 변하기 어려운 것에 의존한다**(안전 의존성 원칙).

- 레이어를 나누는 이유는 **변경 정도가 비슷한 모듈을 응집**하기 위해서다 — 추출 가능해 보여도
  변경 위계가 같으면 그대로 둔다. 한 곳에서만 쓰는 서비스는 그 모듈이 흡수한다
- 상위 레이어는 **조립만** 한다. 요구사항 변경은 도메인 모듈이 흡수한다
- 하위가 그대로인데 문제가 생겼다면 상위를 의심한다
- 상위 변경이 하위에 영향을 준다면 하위 인터페이스를 잘못 썼거나 설계가 틀렸다

**하위가 상위 기능을 필요로 하면** 하위가 필요한 능력만 **포트로 선언**하고 상위가 구현해 주입한다.
도메인은 어떤 외부 구현인지 몰라야 하고, 교체는 어댑터 한 파일로 끝나야 한다.

인터페이스 계약이 바뀌면 그것을 구현한 상위 전부가 영향을 받는다 — 처음에 신중히 정하고,
바꿔야 하면 하위 호환을 지킨다.

## 3. 제공자는 소비자를 모른다

- 하위 모듈이 화면 이름·호출자로 분기하면 오염이다. 조회 범위·페이지 크기는 화면의 정책이다
- 하위는 **질의 능력만 도메인 어휘로 노출**하고 조합은 소비자가 한다
- **패턴은 알고, 개별 소비자는 모른다** — 어떤 사용이 있는지 알아야 인자를 열 수 있지만
  특정 소비자를 알아서는 안 된다
- 이벤트도 같다. 스키마에 소비자용 정보나 생산자 관심사 밖의 정보를 넣지 않는다

## 4. 들어오는 데이터는 경계에서 자기 언어로 바꾼다

런타임 검증과 변환을 **한 지점에서 끝낸다.** 변환 없이 통과시키면 외부 변경이 안쪽까지 전파된다.

- optional 덩어리를 상태별 discriminated union으로 바꾼다 — 보장 안 된 필드 접근이 컴파일에서 막힌다
- 계약 위반(상태와 필드가 어긋난 응답)은 경계에서 끊는다. 화면까지 흘러가 터지는 것보다 빠르다
- **공개 API만 내보낸다.** 스키마·파서를 함께 내보내면 소비자가 다시 외부 응답 형태에 의존한다
- 검증은 인터페이스 진입점에서만. 타입이 보장하는 것을 런타임 가드로 다시 막지 않는다

## 5. 쓰기는 한 곳에서만

읽기와 쓰기를 나누고 쓰기 권한은 한 모듈만 갖는다(CQRS). 변경 지점이 예측 가능해지고 캐시·재시도
정책을 한 곳에서 정한다. 멱등키 같은 **보장 규칙은 도메인이 만든다** — 호출부가 만들면 보장이 흩어진다.

## 6. 구현 디테일이 계약을 넘어오면 추상화가 샌다

- **CQS** — 조회는 상태를 바꾸지 않고, 명령은 상태를 바꾸되 값을 반환하지 않는다
- **Temporal coupling** — "B 전에 A를 반드시 호출"이 호출자 기억에 맡겨지면 그 결합은 캡슐화되지
  못하고 사용처마다 복제된다
- **Leaky abstraction** — 안쪽 사정을 알아야만 바르게 쓸 수 있으면 이미 샌 것이다

## 7. 이름이 책임을 정확히 서술한다

- 절반만 서술하는 이름, 다른 개념과 혼동될 이름을 쓰지 않는다
- **곧 걷어낼 모듈에 범용 이름을 붙이지 않는다** — 범용 이름을 주면 다른 곳에서 끌어다 쓰게 되어
  제거가 어려워진다. 의도적으로 좁은 이름을 쓴다
- 유틸을 `utils`/`helpers`에 쌓지 말고 목적이 분명한 라이브러리 단위로 쪼갠다

## 8. 소비처가 지불할 비용을 먼저 본다

- 내부 타입 분기가 공용 사용처로 새면 안 된다 — 필요하면 평평하게 펼쳐 노출한다
- 함수는 실제로 필요한 것만 받는다. 응답 DTO를 통째로 넘기면 중복 검사와 불필요한 의존이 따라온다

## 위반 신호

- 하위 모듈 시그니처에 호출자·화면을 뜻하는 인자가 있다 (`from: 'admin' | 'checkout'`)
- 같은 계산이 두 파일에 복사돼 각자 자랐다
- 외부 응답 타입이 도메인 안쪽까지 그대로 흘러간다 / 스키마가 함께 export 된다
- 조회 함수가 상태를 바꾼다 (생성·복구·정산)
- 한 함수가 서버 응답·권한·국제화·정책의 언어를 동시에 쓴다
- 두 모듈이 서로를 import 한다
- 인터페이스는 나뉘었는데 한쪽을 고칠 때마다 다른 쪽도 같이 고친다
