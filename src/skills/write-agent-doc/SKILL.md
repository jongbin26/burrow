# 에이전트 지침 문서 작성 스킬

코드베이스를 분석해 **에이전트가 이 폴더에서 일할 때의 규칙(Do/Don't)**을 쓴다.
코드로 초안 → 모호한 부분만 질문 → 아래 원칙으로 self-review.

## 비목표

- 기존 문서 리포맷/압축 → 본 스킬 비목표
- 자동 커밋/PR → 사용자가 한다
- 상위 에이전트 지침 내용 중복 → 상위에 있으면 다시 쓰지 않는다
- 사용 설명서/API 레퍼런스 → README 영역. 이 문서는 "수정자가 무엇을 지킬지"다

## 분량 기준 (가장 중요)

**분량은 복잡도에 비례한다 — 비자명한 정보량만큼만.** 작은 폴더(몇 파일)는 `Description` + `Do`/`Don't`로 ~30줄이면 끝. 복잡한 도메인 모듈(여러 협력자·라이프사이클)은 그만큼 늘되 권장 상한 **~150줄**을 넘기지 않는다(프로젝트가 별도 상한을 정했으면 그것을 우선).
섹션을 채우려 하지 마라 — **도출 불가한 것만** 넣는다(파일 목록·자명한 패턴은 Glob로 알 수 있으니 제외). 매 턴 로드되므로 모든 줄이 토큰 비용이다.

## 원칙

1. **짧고 명령형·구체적·개조식으로** — 종결형으로 끊는다: "갱신한다"→"갱신", Don't는 "~ 금지". 수식어·인사말·대명사("그것")·"적절히/필요시" 금지. "코드를 깔끔하게" ❌ → "함수 30줄 이내, named export만" ⭕. 비자명한 규칙엔 good/bad 예시 1개.
2. **Do / Don't 분리** — Don't엔 Do의 부정("X 하라"의 반대)을 다시 쓰지 말고, Do로 안 잡히는 **고유 안티패턴**만 적는다.
3. **검증 가능하게** — 에이전트가 따랐는지 스스로 확인 가능한 규칙으로.
4. **주장은 구현 코드로 검증** — "폴링/exhaustive/타입이 막아준다" 같은 동작 단정은 **구현 코드**에 그 장치(`switch`+`never`, 폴링 루프 등)가 실제 있는지 확인하고 쓴다. 테스트·주석은 stale일 수 있으니 기준이 아니다.

## 워크플로우

### Step 1: 대상 결정

- 대화 맥락 또는 인자에서 대상 디렉터리를 정한다. 명백하면 바로 진행.
- 정말 모호할 때만 사용 가능한 질문 수단으로 한 번 확인.
- 대상 문서가 **이미 있으면** 기존 내용을 읽고 요청 범위에 맞게 갱신한다. 보존할 내용과 충돌해 판단할 수 없을 때만 묻는다.

### Step 2: 코드 분석 (자동 초안)

대상을 `Glob`/`Read`로 읽어 채운다.

- **구조·패턴** — 파일 레이아웃, 네이밍, 반복 패턴 (필수 규칙이면 Do로)
- **상위 AGENTS.md 또는 CLAUDE.md** — 이미 정의된 규칙은 중복하지 않는다
- **동작은 구현으로 확인** — "폴링/구독/단발호출" 같은 서술은 추측 말고 코드로 (`.then()` 1회 = 폴링 아님)
- **공개 계약** — 핵심 산출물이 공개 export(훅/컴포넌트/API)면 사용처를 grep해 소비처가 의존하는 계약(반환 형태·호출 순서)을 파악하고 **Do 제약**으로 쓴다 ("반환 형태 `{…}`는 공개 계약이다 — 변경 시 소비처가 깨진다"). 근거는 **계약의 존재**에 호소하고, "소비처가 X처럼 쓴다"는 특정 사용 방식은 적지 마라 — 다른 소비처는 다르게 쓸 수 있어 언제든 틀려진다. 사용처 이름·줄번호도 금지.

### Step 3: 빈칸만 인터뷰

코드로 알 수 없는 것만 사용 가능한 질문 수단으로 확인한다: 핵심 목적 / Do / 흔한 안티패턴.

### Step 4: 문서 생성

**필수**: `Description`(1-3줄), `Do`, `Don't`.
**조건부** — 둘 다 "코드만 읽어선 못 알아내는 것"일 때만:
- `경계` + `판단 기준` — 형제 폴더와 책임이 겹쳐 "이 로직 어디 두지"가 헷갈릴 때. 에이전트가 가장 자주 틀리는 지점.
- `구조·흐름`(또는 `생명주기`) — 여러 부분이 비자명하게 상호작용하거나 데이터 흐름·라이프사이클이 코드만으론 안 잡힐 때. **관계·순서만 적고 파일 목록은 금지**(파일 나열은 Glob로 도출 가능). 단순하면 Description의 한 줄 흐름(`A → B → race → C`)으로 충분.

- Do/Don't 항목은 한 줄로 단정하게.
- 흐름 표기: **선형이면 한 줄 텍스트**(`A → B → race → C`). **분기·팬아웃·순환·상태전이·트리처럼 비선형 토폴로지가 비자명할 때만 작은 mermaid**(노드 ~7개 이내). 선형에 mermaid 금지 — 텍스트가 더 짧다.
- 상위 섹션과 겹치는 섹션은 넣지 않는다.

### Step 5: Self-review

- [ ] 모호한 표현/대명사가 없는가
- [ ] Don't가 Do의 단순 부정이 아닌가
- [ ] 동작·메커니즘 단정이 **구현 코드**와 일치하는가 (테스트·주석 말고)
- [ ] 모든 줄이 도출 불가한가 (파일 목록·자명한 패턴 없는가) / 빈 껍데기 섹션이 없는가
- [ ] `구조·흐름`을 넣었다면 관계·순서만인가 (파일 나열이 아닌가) / mermaid는 비선형 토폴로지일 때만 썼는가

### Step 6: 마무리

최종 경로를 안내한다. **커밋하지 않는다.**
