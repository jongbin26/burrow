# 설계 합의 충실도

최신 설계 합의가 계획과 코드, 검증에서 같은 의미로 남아 있는가.
뿌리: 동작이 맞는 것과 합의한 구조가 만들어진 것은 별개다. 합의는 기억이 아니라 관측 가능한 완료 조건으로 옮긴다.

## 1. 구현 전에 최신 합의와 거부한 대안을 함께 고정한다

대화가 길어지면 처음 제안, 교정된 안, 임시 타협이 섞인다. 마지막으로 받아들인 결정만 목표로 두고, 명시적으로 거부한 모양도 음의 조건으로 남긴다.
판정 질문: 반드시 성립할 것, 남으면 안 될 것, 임시 허용, 이번 범위 밖을 각각 한 줄로 적었나? 저장소 문서나 기존 계획이 최신 합의와 충돌하면 코딩 전에 드러냈나?

## 2. 합의를 구현 주인과 검증 근거에 연결한다

좋은 방향이라는 서술만으로는 구현 중 책임이 다른 레이어로 밀려가도 알아채기 어렵다. 결정마다 누가 보장하고 무엇으로 확인할지 정한다.
판정 질문: 각 결정에 책임지는 모듈과 코드·타입·테스트·검색 중 하나의 근거가 연결돼 있나? 동작 테스트만으로 구조 조건까지 충족했다고 간주하지 않았나?

## 3. 새 계약은 거부한 기존 계약을 원본으로 삼지 않는다

호환이 필요해도 새 경로가 옛 표현을 입력으로 받아 번역하면 결함은 사라지지 않고 새 경계 안으로 이동한다. 호환 어댑터는 새 계약에서 기존 소비처를 향해야 한다.
판정 질문: 호환 계층을 지워도 새 계약이 독립적으로 완전한가? 새 API가 교체하기로 한 타입·분기·호출 순서를 직접 소비하지 않나?

## 4. diff 밖의 생산자와 소비자까지 따라가서 검증한다

새 wrapper의 출력만 보면 기존 결함이 상류에 남은 것을 놓친다. 바뀐 파일뿐 아니라 값이나 명령을 만드는 곳부터 최종 실행하는 곳까지 확인한다.
판정 질문: 새 경계의 입력 생산자와 출력 소비자를 실제로 열어 봤나? 거부한 이름과 구조를 전체 영향 경로에서 검색했나?

## 5. 완료 전에 충족·부분 충족·연기·누락을 구분한다

외부에서 안 보인다는 이유로 내부에 남은 결함을 완료로 부르면 후속 작업이 사라진다. 임시 타협은 제거 조건과 후속 단위가 있을 때만 연기로 분류한다.
판정 질문: 합의마다 판정을 붙였고 부분 충족을 완료로 보고하지 않았나? 연기한 항목에는 임시 경계, 제거 조건, 후속 작업이 모두 있나?

## 6. 반복된 유실은 가장 작은 실행 장치로 막는다

같은 거부 조건을 두 번 놓쳤다면 다음 리뷰어의 기억에 맡기지 않는다. 식별 가능한 import·export·타입·호출 방향은 lint나 계약 테스트로 막고, 기계화할 수 없는 판단만 문서에 둔다.
검사는 제거한 식별자의 문자열이 아니라 책임·의존 방향·공개 계약 같은 invariant를 고정해야 한다. 이름만 바꾼 같은 결함도 거부하고 지원되는 다른 구현은 받아들이는지 확인한다. 이 둘을 구분하지 못하면 구조 조건을 기계화한 것으로 보지 않는다.
판정 질문: 검사가 이름을 바꾼 같은 결함도 거부하고 지원되는 구현은 받아들이나? 식별자 문자열을 바꾸면 우회되는 검사를 구조 조건의 근거로 쓰지 않았나?

## 위반 신호

- 최신 합의 대신 저장소의 오래된 문서나 첫 제안을 구현 기준으로 삼는다
- 외부 결과 타입만 정리되고 바로 상류의 혼합 타입과 중앙 switch는 그대로다
- 새 API가 제거하기로 한 기존 계약을 import해 번역한다
- PR 설명은 책임 제거를 말하지만 diff는 실행 위치만 옮긴다
- 테스트 통과를 구조 조건의 근거로도 사용한다
- 임시 코드에 제거 조건이나 후속 작업이 없다
- 같은 설계 교정이 반복되는데 이를 거부하는 타입·lint·계약 테스트가 없다
- 제거한 타입·함수 이름의 문자열 검색을 구조 검증으로 간주한다
