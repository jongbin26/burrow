# 관측 계측

**관측은 로그가 아니라 사용자 경험 추적이다.** 단발 이벤트를 흩뿌리는 것이 목표가 아니라
요청·진행·결과·실패를 하나의 흐름으로 잇는 것이 목표다. 아래 규칙은 작성 기준이자 리뷰 기준이다.

## 0. 도구의 기본값을 먼저 확인한다

에러 추적기·제품 분석·RUM·메트릭 백엔드는 자동 동작과 과금 모델이 서로 다르다. **아래를 쓰는 도구의
문서에서 확정한 뒤 계측을 설계하고, 확정한 답은 그 프로젝트 문서에 적는다** — 다음 사람이 다시 찾지 않게.

| 확인할 것 | 갈리는 예 (도구 문서로 재확인) | 이 답이 바꾸는 규칙 |
|---|---|---|
| 무엇이 자동 캡처되나 | Datadog RUM은 `console.error`도 RUM Error로 승격 / Sentry는 기본이 breadcrumb (에러 승격은 별도 설정). 둘 다 unhandled·rejection은 자동 | 1, 3, 4 |
| 무엇이 grouping하나 | 이름 필드(`@action.name`) / stack·메시지 fingerprint | 2 |
| 과금·인덱싱 단위 | 세션 단위(속성 카디널리티가 비용에 무관) / 이벤트·속성 단위, 태그 상한 있음 | 3, 6 |
| 샘플링이 걸려 있나 | `tracesSampleRate` 류의 클라이언트 샘플링, 백엔드 인덱싱 샘플링 | 8 |
| 세션·유저 귀속이 자동인가 | RUM은 session·view에 자동 귀속 / 수동 태깅 필요한 도구 | 5 |
| 서버 trace 연결 조건 | 전파 허용 origin 목록(`allowedTracingUrls` 류)에 든 요청만 | 5 |

## 1. 신호와 로그를 가른다

관측 신호(흐름·사용자 영향 오류)는 관측 SDK로 발행하고, 순수 진단 로그는 로거로 남긴다.
둘을 섞으면 대시보드가 진단 노이즈를 세고, 에러 추적이 로그로 오염된다.

**자동 캡처되는 것을 다시 발행하지 않는다.** Datadog RUM에서는 로그 목적의 `console.error` 한 줄이
그대로 RUM Error가 되어 에러 추적을 오염시킨다 — Sentry에서는 기본이 breadcrumb이라 같은 코드가
다르게 동작한다. 어느 쪽인지는 0번에서 확정한다.

실패한 fetch·XHR도 도구에 따라 Resource 이벤트일 뿐 에러가 아니다. 자동으로 잡힌다고 믿고 안 남기거나,
이미 잡힌 걸 또 남기는 양쪽 다 확인 없이 나온다.

## 2. 이름은 흐름 1단위

이벤트 이름은 `<도메인>_<흐름>` 하나로 두고, 집계는 그 이름으로 묶는다.

- 성패·단계를 이름에 합치지 않는다(`_success`/`_fail`/`.start` 분할 ❌) — 흐름이 이름마다 쪼개진다
- 전송 기술이 아니라 **도메인**을 기준으로 짓는다. 팀·조직명 prefix 금지 — 팀명은 변한다
- 라벨은 서술형 문장이 아니라 도메인 명사형이다. 문구가 바뀌면 grouping이 깨진다
- 도구가 메시지·stack으로 자동 grouping한다면(0번), 그 fingerprint가 무엇에 매달려 있는지 알고 이름을 짓는다

```ts
addAction('sse_download_success')                          // ❌ 성패가 이름으로 갈림
addAction('WEB-A-sse-download')                            // ❌ 팀명 prefix
addAction('sse_download', { phase: 'result', outcome: 'success' })   // ⭕
```


## 3. 성패·단계·사유는 필드, 발행은 조사 가치 있는 전환만

발행 한 번은 각각 별도 이벤트다(같은 이벤트의 갱신이 아니다).

- `outcome`(success/fail/fallback)은 **종료 단계에서만**, 나머지는 `phase`·`reason`으로 나눈다
- 재시도 루프·단순 progress tick마다 발행하지 않는다. SDK가 자동 기록하는 상호작용도 중복 금지
- 판정 결과 boolean(`isExpected`)으로 동결하지 않는다 — 사실 필드(`reason`·`code`)로 남겨야 나중에 다시 판정할 수 있다
- context에 Error 객체·응답 전체·대형 배열을 넣지 않는다
- **고카디널리티 값(상관관계 ID 등)을 필드에 넣어도 되는지는 도구가 정한다**(0번). Datadog RUM처럼 세션 단위로 과금하면 필드를 늘려도 비용이 안 늘지만, 이벤트·속성 단위로 과금하거나 태그 개수·길이에 상한이 있는 도구에서는 같은 설계가 비용·유실로 돌아온다

## 4. 예상된 실패는 에러가 아니다

- 예상된 비즈니스 실패·정상 fallback → 이벤트의 `outcome: fail|fallback`. 에러 추적에 넣지 않는다.
  에러 추적은 "사람이 고쳐야 할 것"의 목록이고, 정상 경로가 섞이면 알림이 무뎌진다
- 처리된 예외 중 **디버깅할 stack이 필요한 사용자 영향 오류** → 에러로 발행
- 실패율 집계와 stack 디버깅이 둘 다 필요하면 같은 상관관계 ID로 두 신호를 잇고, 각각의 집계 목적을 명시한다

```ts
catch (e) { addError(e) }                                  // ❌ 정원 초과·validation 실패도 에러 목록에 쌓임
catch (e) { addAction('team_invite', { phase: 'result', outcome: 'fail', reason: 'seat_limit' }) }   // ⭕
```


## 5. 상관관계 ID는 흐름을 갈라야 할 때만

세션·유저·화면 귀속이 자동인 도구라면 그것만으로 충분한 경우가 많다(0번).
**한 세션에서 같은 흐름이 겹쳐 개별 시도를 갈라야 할 때만** 도메인 경계에서 요청마다 유일한 id를
만들어 관련 신호 전부에 같은 키로 넣는다.

- 요청↔결과처럼 묶여야 자연스러운 흐름인데 단발 이벤트만 남기려 하면 — 자동 도입도, 조용한 생략도 금지.
  작성 중이면 구현 전에 한 번 묻고, 리뷰 중이면 멈추지 말고 도입 이득과 생성 위치를 제안한다
- 도메인에 이미 운영 중인 키가 있으면 그것을 쓰고, 신규 흐름의 기본 키는 `correlationId`
- **상관관계 ID는 서버 trace 연결이 아니다.** 같은 id를 넣어도 서버 span에 자동으로 붙지 않는다 —
  trace 연결은 도구가 정한 전파 방식을 별도로 확인한다 — Datadog RUM은 `allowedTracingUrls` 같은 허용 origin 목록에 든 요청에만 헤더를 싣는다. 헤더를 실을 수 없는 요청 방식(beacon·img·일부 SSE 클라이언트)은 애초에 전파되지 않는다
- 흐름을 잇는 채널은 관측 이벤트다. 진단 로거에 상관관계 ID를 넣어 흐름을 이으려 하지 않는다 — 다른 제품·다른 저장소면 같은 쿼리로 묶이지 않는다

## 6. 발행은 SDK가 초기화된 실행 경계에서

계측 직접 호출은 **SDK를 초기화한 호스트 경계**에서 한다. 하위 계층(프레임워크·워커·전송·SSR 공용 entry)은
raw fact만 상향하고, 사용자 영향 판정과 발행은 호스트 경계 호출부가 한다.

하위 계층이 SDK를 import하면 SDK 미초기화 환경에서 조용히 사라지거나 전역 객체를 뒤지는 우회가 생긴다.

메트릭·태그 기반 백엔드로 승격하는 값은 **저카디널리티만** — 상관관계 ID·리소스 id·사용자 id를
태그로 올리지 않는다. 이벤트 속성(3번)과 메트릭 태그는 비용 모델이 다르다.

## 7. 이름을 바꾸기 전에 운영 의존성을 확인한다

이전·rename은 신규·변경 코드부터 한다. 기존 운영 이름을 기능 작업에 섞어 바꾸지 않는다.
불가피하면 dual-write 병행 → 소비처 이관 확인 → 구본 제거.

전환 전에 그 이름에 걸린 **대시보드·알림·저장된 쿼리·자동화·샘플링/보존 규칙**을 조회한다.
**조회가 불가하면(도구 미연결·미인증·권한 없음·headless) "운영 의존성 미확인"으로 표시하고
확인할 query와 범위를 제안한다. 확인 못 한 것을 확인한 것으로 쓰지 않는다.**

## 8. 필드 추가만으로도 모수는 바뀐다

이름·타입을 그대로 둬도 (a) 기존 이벤트에 **새 발행 경로를 합류**시키거나 (b) 기존 필드의
**측정 구간을 옮기면** count·백분위의 의미가 **에러 없이** 달라진다. "additive라 안전하다"는 판단으로
그냥 통과하는 경로라 따로 둔다.

- 발행 경로·측정 구간·발행 빈도를 바꾸기 전에 7번의 의존성 확인 절차를 그대로 밟는다
- 합류가 불가피하면 **기존 계열을 되살릴 구분 필드를 같은 배포에 함께** 넣고, 무엇을 세면 기존 값인지를 문서에 규약으로 남긴다
- 한 사건이 남기는 **이벤트 건수**가 경로마다 다르면 count 위젯이 조용히 섞인다 — 건수를 균일화하거나 세는 기준 필드를 고정한다
- 샘플링이 걸린 채널이면(0번) count는 표본이다. `tracesSampleRate` 류의 값을 바꾸는 것도 모수를 바꾸는 변경이고, 샘플링 단위가 세션이면 세션째로 빠지므로 이벤트 수를 세션 수로 나눈 값이 왜곡된다

## 9. 보내면 안 되는 것

token·cookie·인증 헤더·URL query·사용자 이메일/이름·사용자 입력 원문·문서/clipboard 내용·request/response 전문.

식별자는 조사에 반드시 필요한 최소한만. Error·객체를 context에 넣기 전에 열거 가능한 필드를 펼쳐 민감정보를 제거한다.
도구의 자동 스크러빙에 기대지 않는다 — 무엇을 지우는지는 도구마다 다르고, 커스텀 필드는 대개 대상이 아니다.

## 계측을 추가·리뷰하기 전에

같은 도메인의 기존 이벤트 이름·context 키를 먼저 검색해 일관성을 확인한다. 단 기존 라벨에 팀명
prefix처럼 2번을 어긴 흔적이 있으면 따라가지 않는다. 계측 호출이 하위 계층에 있는지 파일 경로로 확인한다.

## 위반 신호

- 도구가 무엇을 자동 캡처하는지 확인하지 않은 채 계측을 추가했다
- 이벤트 이름이 `_success`/`_fail`/`.start`로 갈려 있거나 팀·조직명 prefix가 붙어 있다
- 재시도 루프·progress tick·전송 계층 connect/disconnect마다 발행한다
- validation 실패·정상 fallback이 에러로 발행된다
- 자동 캡처되는 unhandled·rejection을 다시 에러로 발행한다
- 로그 목적의 `console.error`가 남아 있다
- 하위 계층 파일에 관측 SDK import나 전역 객체 probe(`window.<SDK>`)가 있다
- context에 Error 객체·응답 전체가 통째로 들어간다
- 판정 boolean(`isExpected`)만 남기고 사유 필드가 없다
- 측정 시작·종료 지점을 옮기는 리팩터인데 소비처 확인 흔적이 없다
- 성격이 다른 발행부가 기존 이벤트 이름에 합류했는데 구분 필드가 없다
- 모수가 다른 두 필드를 한 위젯에서 사칙연산한다
- 샘플링된 채널의 count를 절대 건수로 읽는다
- "확인했다"고 적혀 있는데 조회 근거가 없다
