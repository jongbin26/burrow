# 가독성 패스

테스트·타입·린트는 동작을 본다. 이 패스는 다음 사람이 읽을 수 있는지를 본다. 통과한 검사로 끝을 판정하면 수백 줄짜리 함수도 어떤 신호를 내지 않으므로, 보고 전에 한 번 따로 돈다.

## 절차

1. 이번 작업에서 바뀐 파일 목록을 뽑는다 (`git diff --name-only` 또는 작업 시작 커밋 기준)
2. 파일마다 네 가지를 적는다. 보고에 싣지 않고 판정에만 쓴다
   - 책임 한 문장 (처음 보는 사람에게 설명한다면)
   - 이 파일이 바뀌는 이유 목록
   - 가장 긴 함수의 줄 수와 그 함수 범위의 가변 변수 수
   - 파일 지도에 이 파일의 행이 있는지
3. 하나라도 걸리면 멈추고 cohesion의 판정 질문으로 가른다
   - 책임이 한 문장으로 안 된다
   - 바뀌는 이유가 둘 이상이다
   - 함수 범위의 가변 변수가 셋 이상이다
   - 린트 한도(없으면 파일 200줄·함수 60줄)를 넘는다
   - 파일 지도에 행이 없다
   - nullable·boolean 필드 서넛의 조합이 모드를 가리고 그 해독이 함수마다 반복된다 (type-modeling 7)
4. 갈랐으면 2로 돌아간다. 가르지 않기로 했으면 그 이유를 보고에 한 줄 적는다
5. 이번 diff가 새로 만들거나 바꾼 이름을 뽑는다. 내보내는 이름, 포트·인터페이스의 메서드, 메시지·상태·결과의 종류 값이 대상이고, 다른 자리에서 옮겨 온 이름도 넣는다
   - 이름마다 부르는 자리 한 줄을 실제 코드에서 옮겨 적고, 그 줄만 읽고 하는 일이 읽히는지 본다
   - 후보를 적는다: 리뷰어가 낸 이름, 기대는 플랫폼·언어·프레임워크가 같은 일에 쓰는 이름, 개발자가 흔히 쓰는 말
   - abstraction 4의 판정 질문에 답하고 걸리면 고친다. 리뷰어가 낸 이름과 다르게 갔다면 이유를 보고에 적는다
6. 파일 지도 검사 스크립트를 돌린다 (file-map). 새 파일이 생겼는데 지도가 그대로면 지도를 고친다
7. 보고 끝에 한 줄로 적는다: 패스한 파일 수, 가른 파일 수, 가르지 않고 둔 파일과 이유, 다시 지은 이름 수

## 지키는 것

- 테스트가 통과했다고 건너뛰지 않는다. 통과한 뒤에 하는 것이다
- 한 파일에 "기존 패턴을 따라 추가"했을 뿐이라도 돈다. 누적은 그런 추가로만 온다
- 설명 문장을 보고에 길게 싣지 않는다. 판정 결과만 적는다
- 가르는 작업이 이번 요청 범위를 넘으면 가르지 않고 보고에 남긴다 (change-scope). 그래도 지도의 행은 고친다

## 위반 신호

- 보고에 패스 결과 줄이 없다
- "테스트 통과"가 끝의 근거로만 적혀 있다
- 새 파일이 생긴 diff에 README 지도 변경이 없다
- 새 이름이 생긴 diff인데 부르는 자리를 읽어 본 흔적 없이 보고했다. 구조를 바꾸면서 옛 낱말을 새 메시지·상태 이름으로 그대로 이어 썼다
- 같은 파일이 세 번째 작업에서도 "기존 패턴 추가"로 커졌는데 패스가 걸리지 않았다
